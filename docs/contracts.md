# Общие классы

Агента, скил и систему оценки пишут три разных человека. Чтобы их части работали вместе, все передают данные друг другу через одни и те же классы. Эти классы описаны ниже.

Сергей первым делом создаёт их в файле `agent/types.py`. После этого правильной считается версия в коде. Если меняешь что-то в этом файле, предупреди остальных, потому что это затронет их код.

Значения слов «модель», «сообщение», «ход», «скил», «заметки» и других объяснены в разделе «Основные понятия» в [architecture.md](architecture.md).

Почти все классы ниже — это `dataclass`, то есть обычные классы, которые только хранят данные и не содержат логики.

## Вызов модели

```python
Message = dict   # {"role": "system" | "user" | "assistant", "content": str}

@dataclass
class Usage:
    input_tokens: int = 0
    output_tokens: int = 0

@dataclass
class LLMResponse:
    text: str
    usage: Usage
    tool_calls: list[dict] = field(default_factory=list)

class LLMClient(Protocol):
    def complete(self, messages: list[Message], json_schema: dict | None = None,
                 temperature: float = 0.0) -> LLMResponse: ...
```

`Message` — одно сообщение переписки. Это обычный словарь с двумя ключами: `role` (чьё сообщение) и `content` (текст). Отдельный класс не делаем, потому что API моделей принимает именно такие словари, и их можно передавать без преобразований.

`Usage` хранит, сколько токенов ушло на вызов модели: на входе (`input_tokens`) и на выходе (`output_tokens`). По этим числам считаем стоимость.

`LLMResponse` — ответ модели: текст ответа и расход токенов. Поле `tool_calls` пока всегда пустое. Оно понадобится, когда агент научится пользоваться инструментами.

`LLMClient` описывает, как выглядит любой LLM-клиент. У него один метод `complete`, параметры такие:

| Параметр | Что значит |
| --- | --- |
| `messages` | список сообщений, которые отправляем модели |
| `json_schema` | если передан, модель обязана вернуть ответ в виде JSON с полями, описанными в этой схеме. Нужно, когда ответ модели разбирает программа, а не читает человек. Если не передан, модель отвечает обычным текстом |
| `temperature` | насколько случайным может быть ответ. При 0 модель на одинаковый запрос отвечает почти одинаково, поэтому в экспериментах используем 0 |

`LLMClient` объявлен как `Protocol`. Это значит, что LLM-клиентом считается любой класс, у которого есть метод `complete` с такими параметрами. Наследоваться ни от чего не нужно.

## Журнал событий (трасса)

```python
@dataclass
class Event:
    kind: str
    name: str
    data: dict
    ms: int = 0
    usage: Usage | None = None
```

`Event` — одна запись в журнале событий диалога.

| Поле | Что хранит |
| --- | --- |
| `kind` | тип события: `skill` (скил принял решение), `llm` (был вызов модели), `error` (скил упал с ошибкой) |
| `name` | какой скил или какая модель |
| `data` | подробности, их состав зависит от типа события |
| `ms` | сколько миллисекунд это заняло |
| `usage` | сколько токенов потрачено, заполняется только для вызовов модели |

## Скил

```python
@dataclass
class Turn:
    history: list[Message]
    user_text: str
    llm: LLMClient
    notes: list[str]
    state: dict
    trace: list[Event]

@dataclass
class Reply:
    text: str
    data: dict = field(default_factory=dict)

@dataclass
class Continue:
    pass

class Skill:
    name = "base"
    def __init__(self, **options): self.options = options
    def before(self, turn: Turn) -> Reply | Continue: return Continue()
    def after(self, turn: Turn, reply: str) -> str: return reply
```

`Turn` — набор данных, который агент передаёт скилу в каждом ходе.

| Поле | Что хранит |
| --- | --- |
| `history` | все сообщения диалога, включая только что пришедшее сообщение пользователя |
| `user_text` | текст только что пришедшего сообщения пользователя |
| `llm` | LLM-клиент, через который скил может сам обратиться к модели. Все такие обращения автоматически записываются в журнал событий |
| `notes` | список заметок для модели. Скил добавляет сюда строки, агент вставляет их в системный промпт этого хода |
| `state` | словарь, в котором скил хранит свои данные между ходами одного диалога. У каждого скила свой словарь, чужие данные скил не видит |
| `trace` | журнал событий диалога |

Хук `before` должен вернуть одно из двух:

| Что вернуть | Что сделает агент |
| --- | --- |
| `Reply` | отправит пользователю текст из поля `text` и закончит ход. Модель в этом ходе вызвана не будет. Поле `data` записывается в журнал событий и нужно только для отладки |
| `Continue` | перейдёт к следующему скилу, а после всех скилов вызовет модель |

`Skill` — базовый класс, от которого наследуются все скилы. В конструктор передаются параметры скила из конфига, внутри скила они доступны как `self.options`. Если скил не переопределяет `before`, ход просто идёт дальше. Если не переопределяет `after`, ответ модели не меняется. Поэтому конкретному скилу достаточно переопределить только то, что ему нужно.

## Агент

```python
class Agent:
    def __init__(self, llm: LLMClient, system_prompt: str, skills: list[Skill]): ...
    def send(self, text: str) -> str: ...
    history: list[Message]
    trace: list[Event]
```

При создании агент получает LLM-клиент, текст системного промпта и список скилов. Скилы вызываются в том порядке, в котором стоят в списке.

Метод `send` принимает очередное сообщение пользователя и возвращает ответ агента. Что происходит внутри, описано в разделе «Как проходит ход» в [architecture.md](architecture.md).

`history` хранит историю диалога, `trace` хранит журнал событий.

Один объект `Agent` ведёт один диалог. Для нового диалога создаётся новый агент.

## Правила

- Когда скил отвечает пользователю сам через `Reply`, агент добавляет этот ответ в историю от имени агента. Поэтому на следующих ходах его видят и модель, и симулятор пользователя.
- Метрики считаются только по разметке судьи, а не по полю `Reply.data`. Иначе нельзя было бы сравнить конфиги, в которых скила нет.
- Если скил упал с ошибкой, ход не прерывается. Агент записывает ошибку в журнал событий и продолжает так, как будто скил вернул `Continue`.
- Код, которому нужна модель, не создаёт LLM-клиент сам, а получает его параметром. Только так в тестах можно подставить ненастоящую модель `FakeLLM`.
