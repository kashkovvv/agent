# Задачи

Здесь у каждого свой план работы: этапы идут в том порядке, в котором их удобно делать. Внутри этапа список шагов, в конце строка «Результат», по которой понятно, что этап закрыт. Что значат упомянутые классы и слова, объяснено в [architecture.md](architecture.md) и в документе каждого участника.

К каждому этапу, где пишется код, пишем и автоматические тесты. Тесты не должны обращаться к настоящим моделям и к интернету, вместо модели используется `FakeLLM`.

Первые три этапа Сергея нужны остальным, чтобы начать писать код, поэтому он делает их в самом начале. Пока они не готовы, Родион пишет текстовую версию скила, а Егор переносит тест-кейсы в файлы и пишет подсчёт метрик. Для этого код Сергея не нужен.

## Сергей

### 1. Подготовить репозиторий

- [ ] Создать `pyproject.toml`, файл с описанием проекта и его зависимостей: Python 3.11 или новее, библиотеки `openai` (для вызова моделей) и `pyyaml` (для чтения YAML). Для разработки: `pytest` (запуск тестов) и `ruff` (проверка стиля кода).
- [ ] Создать папки `agent/`, `skills/`, `configs/`, `evals/`, `tests/` по структуре из [README](README.md).
- [ ] Создать `.gitignore`, чтобы в репозиторий не попадали результаты прогонов, кэш, ключи доступа и служебные файлы Python.
- [ ] Создать `.env.example`, образец файла с ключом доступа к OpenRouter. Сам ключ каждый хранит у себя в `.env`, в репозиторий он не попадает.
- [ ] Настроить GitHub Actions, чтобы при каждой отправке кода на GitHub автоматически запускались тесты и проверка стиля.
- [ ] Описать в корневом README, как установить зависимости и запустить тесты.

Результат: после установки зависимостей команда `pytest` работает и у всех на компьютерах, и на GitHub.

### 2. Общие классы

- [ ] Создать `agent/types.py` с классами из [contracts.md](contracts.md).
- [ ] Показать Егору и Родиону и поправить, если им чего-то не хватает.

Результат: остальные могут использовать общие классы в своём коде.

### 3. Ненастоящая модель для тестов

- [ ] `FakeLLM`: возвращает заранее заданные ответы по очереди или вычисляет ответ функцией от входящих сообщений; запоминает все запросы; если заданные ответы закончились, сообщает об этом понятной ошибкой.
- [ ] `TracedLLM`: передаёт запрос другому клиенту и записывает в журнал событий модель, время и токены.
- [ ] Тесты на оба класса.

Результат: все могут писать тесты для кода, который обращается к модели.

### 4. Агент

- [ ] Класс `Agent` с историей диалога, журналом событий и отдельным состоянием для каждого скила.
- [ ] Метод `send` по пяти шагам из [orchestration.md](orchestration.md).
- [ ] Добавление заметок скилов в системный промпт.
- [ ] Если скил упал с ошибкой, записать её в журнал событий и продолжить ход.
- [ ] Тесты: агент без скилов; скил, который отвечает сам, прерывает ход и модель не вызывается; заметки попадают в системный промпт; метод `after` меняет ответ; ошибка в скиле не прерывает ход; два скила не видят состояние друг друга.

Результат: агент работает с ненастоящей моделью и тестовыми скилами.

### 5. Подключение настоящих моделей

- [ ] `OpenAICompatLLM`: отправляет запрос в OpenRouter, ключ берёт из переменной окружения `OPENROUTER_API_KEY`, возвращает текст и число токенов.
- [ ] Поддержка структурированного ответа: если передан `json_schema`, просить модель вернуть JSON такой формы.
- [ ] При временной ошибке сервиса (перегрузка, сбой сети) один раз повторить запрос, при повторной ошибке сообщить о ней.
- [ ] Тест без реальной отправки запроса: проверить, что запрос собирается правильно и повтор срабатывает.
- [ ] Вручную проверить две модели: одну открытую (Qwen или DeepSeek) и одну сильную коммерческую. Вместе с командой выбрать модели для экспериментов.

Результат: агент отвечает через настоящую модель.

### 6. Файлы настроек

- [ ] Чтение конфига из YAML и создание по нему агента.
- [ ] Реестр скилов: словарь «имя скила — класс скила». Если в конфиге указан неизвестный скил, выдавать понятную ошибку.
- [ ] Базовый системный промпт `prompts/base.md`: агент помогает писать код и присылает код одним блоком.
- [ ] Три конфига: `bare`, `prompt_only` (подключает текстовые правила скила от Родиона), `clarification`.
- [ ] Тесты: из каждого конфига создаётся агент, параметры доходят до скила.

Результат: чтобы поменять вариант агента, достаточно поправить YAML-файл, код трогать не нужно.

### 7. Программа для ручного диалога

- [ ] Консольная программа: при запуске указываются конфиг и модель, дальше человек переписывается с агентом в терминале.
- [ ] Флаг `--trace`: после каждого ответа печатать журнал событий хода.
- [ ] Когда Егор сделает кэш, подключить его.

Результат: варианты `bare` и `prompt_only` можно проверять вручную, а позже и `clarification`.

### 8. Инструменты

Этот этап делается после того, как скил уточнений проверен на тест-кейсах.

- [ ] Общий класс инструмента: название, описание для модели и функция, которая его выполняет. Реестр инструментов и список включённых инструментов в конфиге.
- [ ] Цикл в агенте: если модель просит вызвать инструмент, агент выполняет его, отправляет результат модели и ждёт следующего ответа. Число повторов ограничено.
- [ ] Первые инструменты: прочитать файл, записать файл, запустить код на Python в рабочей папке.
- [ ] Тесты с `FakeLLM`: вызов одного инструмента, нескольких подряд, превышение лимита, запрос несуществующего инструмента.

Результат: можно делать скилы, которым нужны инструменты. На текущую проверку скила это не влияет, там инструменты выключены.

## Родион

### 1. Текстовая версия скила

- [ ] Разобрать тест-кейсы из `skill_test_cases.md`: что в каждом важно уточнить, что агент может решить сам, где ловушки.
- [ ] Написать `skills/clarification/instruction.md`: когда спрашивать и когда нет, не больше трёх вопросов за раз, вопросы нумерованным списком, всё решённое самостоятельно перечислять в блоке «Допущения».
- [ ] Вручную проверить правила в веб-чате двух моделей на кейсах A1, B1, C1, D1. Записать наблюдения в `skills/clarification/notes.md`.
- [ ] Поправить текст по итогам наблюдений.

Результат: готовы правила для варианта `prompt_only`, и есть первое понимание того, как модели ведут себя без скила.

### 2. Симулятор пользователя

- [ ] Класс симулятора в `evals/user_sim.py`: создаётся для конкретного тест-кейса, получает сообщение агента и возвращает ответ пользователя или признак конца диалога.
- [ ] Текст инструкции для модели-симулятора: данные тест-кейса и правила ответов из [clarification-skill.md](clarification-skill.md).
- [ ] В коде: заканчивать диалог, если в ответе агента есть блок кода; считать заданные вопросы (строки, которые заканчиваются знаком вопроса); после пятого вопроса отвечать фиксированной фразой.
- [ ] Тесты с `FakeLLM` на каждое правило.

Результат: Егор может проводить диалоги автоматически.

### 3. Приоритет вопросов

- [ ] Класс недостающей детали: что неизвестно, текст вопроса, оценки I, R, C и отметка, относится ли вопрос к безопасности.
- [ ] Функции: посчитать приоритет, определить, нужно ли уточнять деталь, выбрать вопросы для очередного сообщения.
- [ ] Тесты: формула, порог, вопросы о безопасности всегда нужно уточнять, порядок от важных к менее важным, лимит вопросов.

Результат: выбор вопросов работает и проверен тестами, модель для этого не нужна.

### 4. Поиск недостающих деталей

- [ ] Текст запроса к модели `skills/clarification/prompts/analyze.md`: модели передаются просьба, история и то, что уже уточнено, а она возвращает недостающие детали с оценками.
- [ ] Описание формы ответа для структурированного ответа и функция, которая вызывает модель и превращает ответ в список недостающих деталей.
- [ ] Если модель вернула некорректный JSON, повторить запрос один раз, потом сообщить об ошибке.
- [ ] Тесты с `FakeLLM`: корректный ответ, некорректный ответ, пустой список.
- [ ] Вручную прогнать поиск на всех 13 тест-кейсах и посмотреть, разумны ли оценки.

Результат: по просьбе пользователя получаем список недостающих деталей с приоритетами.

### 5. Скил

- [ ] Что хранить между ходами: исходную просьбу, полученные ответы, допущения, число заданных вопросов, вопросы, на которые ждём ответа.
- [ ] Метод `before` по таблице поведения из [clarification-skill.md](clarification-skill.md).
- [ ] Заметки для модели: что уточнено и какие допущения нужно перечислить.
- [ ] Метод `after`: дописать блок «Допущения», если модель его пропустила.
- [ ] Добавить скил в реестр скилов.
- [ ] Тест на каждую строку таблицы поведения.

Результат: вариант `clarification` работает и в ручном диалоге, и в автоматической проверке.

### 6. Подтверждение задания

- [ ] Параметр `confirm_summary`: после уточнений коротко пересказать задачу пользователю и спросить, всё ли верно. После ответа переходить к написанию кода.
- [ ] Тесты: с параметром и без; если вопросов не было, подтверждение не запрашивается.

Результат: подтверждение можно включить для отдельного эксперимента.

### 7. Эксперименты со скилом

- [ ] Прогнать три варианта агента на выбранных моделях.
- [ ] Разобрать неудачные прогоны по `runs.jsonl`: какие вопросы были лишними, о чём агент не спросил, где не перечислил допущения.
- [ ] Подобрать порог, коэффициенты формулы и тексты `instruction.md` и `analyze.md`.
- [ ] Отдельно сравнить прогоны с подтверждением задания и без.
- [ ] Каждое изменение и его результат записывать в `evals/EXPERIMENTS.md`.

Результат: лучшая версия скила и понимание, что в ней работает.

## Егор

### 1. Тест-кейсы

- [ ] Положить `skill_test_cases.md` в папку `docs/`, это исходник для тест-кейсов.
- [ ] Класс тест-кейса с полями из [evaluation.md](evaluation.md).
- [ ] 13 файлов тест-кейсов в `evals/cases/clarification/`.
- [ ] Функция, которая читает все тест-кейсы из папки.
- [ ] Тесты: все кейсы читаются, нужные поля заполнены, в кейсах A и C есть ответы на все важные детали, минимум вопросов не больше максимума.

Результат: тест-кейсы доступны из кода.

### 2. Метрики

- [ ] Класс разметки судьи: к какой детали относится каждый вопрос агента и что агент сделал с каждой важной деталью (спросил, решил и сказал, решил молча).
- [ ] Функции для всех метрик из [evaluation.md](evaluation.md) и подсчёт итоговых значений по многим прогонам с учётом категорий кейсов.
- [ ] Тесты на разметке, составленной вручную: каждая метрика, случай без вопросов, сумма трёх долей по важным деталям равна единице.

Результат: по разметке считаются все метрики.

### 3. Кэш ответов модели

- [ ] Класс `CachedLLM`: считает хеш запроса, ищет файл с ответом, если не нашёл, вызывает модель и сохраняет ответ.
- [ ] Возможность отключить кэш при запуске.
- [ ] Тесты: повторный одинаковый запрос до модели не доходит; запросы с разными параметрами кэшируются отдельно; при отключённом кэше модель вызывается всегда.

Результат: повторные прогоны не тратят деньги.

### 4. Проверка присланного кода

- [ ] Функция, которая достаёт из ответа агента последний блок кода.
- [ ] Запуск кода на Python вместе с проверками из тест-кейса в отдельном процессе с ограничением 10 секунд. Каждая проверка запускается отдельно, чтобы можно было поставить 1, если прошли все, 0.5, если часть, и 0, если ни одна.
- [ ] Тесты: правильный код, частично правильный, неправильный, зависающий, ответ без кода.

Результат: код на Python проверяется автоматически.

### 5. Судья

- [ ] Текст инструкции для модели-судьи `evals/prompts/judge.md` и описание формы разметки для структурированного ответа.
- [ ] Функция, которая отправляет судье тест-кейс и диалог и возвращает разметку.
- [ ] Для кода не на Python судья дополнительно оценивает, выполнены ли проверки из тест-кейса.
- [ ] Тест с `FakeLLM`: ответ судьи правильно превращается в разметку.
- [ ] Вручную проверить разметку на 3–5 диалогах.

Результат: каждый диалог превращается в разметку для метрик.

### 6. Runner

- [ ] Запуск из консоли с указанием вариантов агента, моделей, числа повторов и возможностью отключить кэш.
- [ ] Один прогон: создать агента, провести диалог с симулятором, отдать диалог судье, проверить код, собрать результат.
- [ ] Прогоны по всем сочетаниям тест-кейсов, вариантов и моделей, запись `runs.jsonl` и `summary.csv`.
- [ ] Вывод итоговой таблицы в консоль.
- [ ] Тест, который проводит один тест-кейс через всю цепочку с `FakeLLM`.

Результат: одна команда выдаёт таблицу метрик по моделям и вариантам агента.

### 7. Прогоны

- [ ] Первый прогон вариантов `bare` и `prompt_only` на выбранных моделях.
- [ ] Вручную проверить разметку судьи примерно на 10 прогонах. Если судья ошибается больше чем в каждом пятом случае, поправить его инструкцию.
- [ ] Прогон с вариантом `clarification`, когда скил готов.
- [ ] Вести журнал экспериментов `evals/EXPERIMENTS.md`.
- [ ] Собрать итоговую таблицу метрик и 2–3 показательных диалога для отчёта.

Результат: есть цифры, по которым видно, помогает ли скил и на каких моделях.
