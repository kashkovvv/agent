# Агент (Сергей)

В этой части агент, через которого идёт весь диалог, классы для вызова моделей, файлы настроек и программа для ручного диалога в терминале. Сюда же входит то, без чего остальным не начать работу: структура репозитория, общие классы из [contracts.md](contracts.md) и ненастоящая модель для тестов.

## Агент

Агент ведёт один диалог. На каждое сообщение пользователя он делает пять шагов:

1. Добавляет сообщение в историю.
2. По очереди вызывает у каждого скила метод `before`. Если какой-то скил ответил сам, агент добавляет его ответ в историю, возвращает пользователю и на этом заканчивает.
3. Собирает сообщения для модели: сначала системный промпт, к которому дописаны заметки скилов, потом вся история. Вызывает модель.
4. Передаёт ответ модели в метод `after` каждого скила. Каждый скил может ответ изменить.
5. Добавляет итоговый ответ в историю и возвращает пользователю.

Код агента должен получиться коротким, порядка сорока строк. Вся сложная логика находится в скилах, а не в агенте.

## Вызов моделей

Все обращения к моделям идут через LLM-клиенты. Их несколько, у всех один и тот же метод `complete`, поэтому они взаимозаменяемы.

| Класс | Зачем нужен |
| --- | --- |
| `OpenAICompatLLM` | Вызывает настоящую модель через OpenRouter. Название модели передаётся при создании, ключ доступа берётся из переменной окружения `OPENROUTER_API_KEY`. Если сервис ответил временной ошибкой (перегрузка, сбой сети), клиент один раз повторяет запрос |
| `FakeLLM` | Ненастоящая модель для тестов. Возвращает ответы, заданные заранее, и запоминает всё, что ей отправили. Модель не вызывает, интернет не нужен |
| `TracedLLM` | Обёртка над другим клиентом. Передаёт запрос дальше и записывает в журнал событий, сколько он занял времени и токенов |
| `CachedLLM` | Обёртка, которая запоминает ответы на диск, чтобы не платить за одинаковые запросы дважды. Делает Егор, подробности в [evaluation.md](evaluation.md) |

Обёртки можно вкладывать друг в друга. При обычной работе клиент собирается так: `TracedLLM(CachedLLM(OpenAICompatLLM(...)))`. Запрос сначала попадает в журнал, потом проверяется в кэше и только если ответа там нет, уходит к настоящей модели.

## Файлы настроек (конфиги)

Вариант агента описывается файлом в формате YAML в папке `configs/`. В файле указаны:

| Поле | Что задаёт |
| --- | --- |
| `name` | название варианта, под ним он попадает в результаты |
| `system_prompt` | путь к файлу с текстом системного промпта |
| `skills` | список включённых скилов. У каждого указано имя и параметры. Порядок в списке — это порядок, в котором агент вызывает скилы |

Чтобы по имени из файла получить класс скила, в коде есть реестр: словарь, где имени скила соответствует его класс. Новый скил нужно добавить в этот словарь.

Модель в конфиге не указывается. Её задают при запуске, чтобы один и тот же вариант агента можно было проверить на разных моделях.

Для экспериментов нужны три конфига:

| Конфиг | Системный промпт | Скилы |
| --- | --- | --- |
| `bare` | базовый промпт из `prompts/base.md` | нет |
| `prompt_only` | базовый промпт и текстовые правила скила из `skills/clarification/instruction.md` | нет |
| `clarification` | базовый промпт | скил уточнений |

## Программа для ручного диалога

Консольная программа (CLI) запускает агента в терминале: человек пишет сообщения, агент отвечает. При запуске указываются конфиг и модель. Если добавить флаг `--trace`, после каждого ответа печатается журнал событий хода: что решили скилы, сколько было вызовов модели и сколько они стоили. Это основной способ отладки.

Задачи по порядку в [tasks.md](tasks.md#сергей).
