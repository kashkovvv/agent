# Проверка скила и данные (Егор)

Эта часть отвечает на вопрос, насколько скил улучшает поведение агента на разных моделях и сколько это стоит. Набор задач для проверки и формулы метрик взяты из `skill_test_cases.md`.

## Как устроена проверка

Проверка идёт автоматически, без участия человека. Для каждого тест-кейса, каждого варианта агента и каждой модели:

1. Создаётся новый агент с нужным конфигом и моделью.
2. Агенту отправляется исходная просьба из тест-кейса.
3. Агент и симулятор пользователя переписываются, пока агент не пришлёт код или не будет достигнут лимит вопросов.
4. Судья читает диалог, размечает уточнения и оценивает присланный код.
5. Код считает метрики по разметке и оценке судьи.
6. Всё сохраняется в файлы.

Программа, которая всё это выполняет, называется runner и лежит в `evals/run.py`. При запуске ей указывают, какие варианты агента и какие модели проверять и сколько раз повторить каждый прогон. Повторы нужны, потому что модель даже при одинаковых условиях иногда отвечает по-разному.

## Тест-кейсы

Каждый тест-кейс из `skill_test_cases.md` переносится в отдельный файл формата YAML в папке `evals/cases/clarification/`. Чтобы добавить новый тест-кейс, достаточно добавить новый файл.

Что хранится в файле тест-кейса:

| Поле | Что означает |
| --- | --- |
| `id` | номер кейса |
| `category` | группа кейса. A: в просьбе не хватает важных деталей, спрашивать нужно. B: просьба описана полностью, спрашивать не нужно. C: часть деталей указана, спрашивать нужно только о недостающих. D: простая задача, на которой проверяем, что агент не задаёт лишних вопросов |
| `prompt` | исходная просьба пользователя |
| `critical` | детали, о которых агент должен спросить, и ответ пользователя на каждую |
| `free` | детали, которые агент может решить сам |
| `expected_questions` | сколько вопросов разумно задать: минимум и максимум |
| `check` | язык решения и текстовые критерии, по которым судья оценивает код |
| `forbidden_questions` | необязательный список тем, о которых агент не должен спрашивать |
| `optional_questions` | необязательный список допустимых уточнений, которые не входят в `critical` |

Сейчас тест-кейсов 13: A1–A4, B1–B3, C1–C3, D1–D3.

Классы данных определены в `evals/case_types.py`: `TestCase`, `CriticalDetail`,
`QuestionRange` и `CodeCheck`. Это dataclass-классы; чтение YAML и преобразование
вложенных словарей в эти классы делает функция `load_cases` в `evals/case_loader.py`.

```python
from evals.case_loader import load_cases

cases = load_cases()  # все кейсы из evals/cases/clarification/
# cases = load_cases("путь/к/другой/папке")
```

Функция возвращает список `TestCase` в порядке имён YAML-файлов. При ошибке
формата данных сообщает имя файла; если папки нет, выдаёт ошибку. Корректность
содержимого кейсов проверяют тесты в `tests/test_cases.py`.

- `critical` — список объектов с полями `id`, `question`, `answer`. Идентификатор
  детали уникален внутри кейса и нужен для ссылок в разметке судьи. В A3 ответ о
  ёмкости выделен из исходного описания `LRUCache(capacity)`.
- `free`, `forbidden_questions`, `optional_questions` — списки строк. Допустимый
  вопрос о пустом списке в D3 не увеличивает число критичных деталей.
- `expected_questions` — объект с целочисленными границами `min` и `max`, включая
  обе границы. Даже для нуля вопросов записываем `{min: 0, max: 0}`.
- `check` содержит только `language` (`python`, `javascript`, `cpp`, `java`) и
  `description` — критерии корректности решения для судьи. Исполняемых проверок
  и служебных имён функций в кейсах больше нет. Имена в примерах условные,
  если они не заданы в самой задаче или ответах пользователя.

## Судья

Одна модель оценивает и качество уточнений, и корректность кода для всех языков.
Ей передаются тест-кейс с критериями и весь диалог. Модель судьи фиксируется для
эксперимента, чтобы все варианты агента оценивались одинаково.

Функция `evaluate_dialogue` находится в `evals/judge.py`, инструкция — в
`evals/prompts/judge.md`. Функция делает один вызов LLM-клиента со структурированным
JSON-ответом и возвращает готовый `RunResult`:

```python
from evals.judge import evaluate_dialogue
from evals.metrics import calculate_metrics

# llm — клиент модели-судьи; model и config относятся к оцениваемому агенту.
result = evaluate_dialogue(llm, case, dialogue, model="agent-model", config="bare")
metrics = calculate_metrics([case], [result])
```

Судья возвращает:

- `questions`: вопросы с признаками `needed` и ссылками `critical_ids`;
- `critical_details`: статус каждой критичной детали — `asked`, `stated`, `silent`;
- `code_score`: оценка корректности кода — `0`, `0.5` или `1`;
- `code_reason`: короткое объяснение оценки кода.

Ответ JSON разбирается в классы данных. Перед возвратом проверяются основные
поля разметки и допустимость оценки. Текст решения не выполняется. Автоматических
повторов запроса нет: ошибка клиента или некорректный ответ передаются вызывающему коду.

Судья может ошибаться. Перед выводами нужно вручную проверить разметку примерно
на десяти диалогах. Тесты интеграции в `tests/test_judge.py` используют заглушку;
качество самой модели этими тестами не проверяется.

## Метрики

Метрики считает обычный код по разметке судьи. Формулы взяты из `skill_test_cases.md`.

| Метрика | Что показывает | Для каких кейсов | Лучшее значение |
| --- | --- | --- | --- |
| Полнота вопросов (QR) | какую долю важных деталей агент уточнил | A, C | 1 |
| Доля озвученных допущений | какую долю важных деталей агент решил сам, но сказал об этом | A, C | |
| Доля решённого молча | какую долю важных деталей агент решил сам и не сказал | A, C | 0 |
| Точность вопросов (QP) | какая доля заданных вопросов была по делу | все | 1 |
| Лишних вопросов на прогон | сколько ненужных вопросов в среднем | все | 0 |
| Попадание в диапазон | в какой доле прогонов число вопросов попало в `expected_questions` | все | 1 |
| Ложные срабатывания | как часто агент спрашивает там, где спрашивать не нужно было вообще | B1–B3, D1, D2 | 0 |
| Корректность кода по оценке судьи | средняя оценка соответствия критериям: 1 полностью, 0.5 частично, 0 нет | все | 1 |

Кроме того, для каждого прогона считается стоимость: сколько потрачено токенов и секунд.

### Данные результата и функции подсчёта

В `evals/case_types.py` добавлены классы для разметки одного прогона:

- `QuestionResult`: `text` — текст вопроса, `needed` — был ли он по делу,
  `critical_ids` — список идентификаторов затронутых критичных деталей.
  Один вопрос может касаться нескольких деталей. У допустимого вопроса D3
  список пустой, но `needed=True`.
- `RunResult`: `case_id`, `model`, `config`, список `questions`, словарь
  `critical_details`, `code_score` (`0`, `0.5` или `1`) и `code_reason`
  с объяснением оценки судьи. В словаре должна быть
  каждая критичная деталь ровно один раз со статусом `asked` (спросил), `stated`
  (решил сам и озвучил) или `silent` (решил молча).

Счётчики и метрики вычисляются в `evals/metrics.py`:

- `count_run(case, result)` — количество вопросов, вопросов по делу, лишних,
  критичных деталей, покрытых деталей, озвученных и молчаливых допущений,
  а также признак попадания в диапазон вопросов.
- `calculate_metrics(cases, results)` — словарь всех восьми метрик для переданных
  прогонов. Сначала складывает счётчики, затем делит их по формулам исходника.
  Повторы одного кейса учитываются как отдельные прогоны.
- `summarize_results(cases, results)` — список строк сводки, сгруппированных по
  паре `model` и `config`. Каждая строка содержит эти два поля и восемь метрик.

Ключи метрик: `qr`, `stated_assumption_rate`, `silent_assumption_rate`, `qp`,
`extra_questions_per_run`, `question_range_rate`, `false_ask_rate`, `code_score`.
Все доли возвращаются в диапазоне 0–1. Если знаменатель равен нулю, значение —
`None`. Для пустого списка прогонов все восемь значений равны `None`, сводка пуста.
При подсчёте проверяются идентификатор кейса, наличие статуса у каждой критичной
детали, допустимые статусы и оценка кода. Связи вопросов с деталями отдельно не
перепроверяются: покрытие считается по статусам в `critical_details`. Поэтому
повторный вопрос о той же детали не увеличивает её покрытие.

```python
from evals.case_loader import load_cases
from evals.metrics import calculate_metrics, summarize_results

cases = load_cases()
# results — список RunResult, заполненный вручную или будущим runner.
metrics = calculate_metrics(cases, results)
summary = summarize_results(cases, results)
```

Функции работают в памяти. Метрика `code_score` — среднее значение оценок
судьи, а не доля выполненных тестов. Учёт токенов и времени, а также запись
`runs.jsonl` и `summary.csv` подключаются вместе с runner.

## Оценка кода

Для Python, JavaScript, C++ и Java используется один подход: судья читает последнее
решение агента и сравнивает его с `case.check.description` и требованиями задачи.

- `1` — по оценке судьи выполнены все критерии;
- `0.5` — выполнена часть критериев;
- `0` — ни один критерий не выполнен, кода нет или решение явно неработоспособно.

Код и присланные агентом тесты не запускаются. Это экспертная оценка модели,
а не доказательство прохождения тестов. Судья не должен заявлять, что выполнял
код, компилировал его или измерял время. Показатель называется «Корректность кода
по оценке судьи», чтобы это ограничение было видно в отчёте.

## Кэш ответов модели

Каждый прогон делает много вызовов модели, и они стоят денег. Чтобы не платить повторно за одинаковые запросы, все вызовы идут через кэш (класс `CachedLLM`).

Кэш работает так. Из названия модели, всех сообщений и параметров запроса считается хеш, то есть короткая строка, которая однозначно соответствует этому запросу. Ответ модели сохраняется в файл с этим хешем в названии. Если такой же запрос придёт ещё раз, ответ берётся из файла, и модель не вызывается.

В итоге повторный прогон без изменений ничего не стоит и даёт те же результаты. Если поменять, например, текст промпта скила, заново вызываются только те запросы, которые от этого изменились. Когда нужно специально получить новые ответы модели, кэш отключается при запуске.

Реализация находится в `evals/cache.py`. Класс принимает готовый LLM-клиент и
имя вызываемой модели. Его метод `complete` имеет тот же интерфейс, что и у клиента:

```python
from evals.cache import CachedLLM

# client — клиент настоящей модели или заглушка с методом complete.
llm = CachedLLM(client=client, model="имя-модели")
response = llm.complete([{"role": "user", "content": "Привет!"}])
```

В ключ SHA-256 входят `model`, все `messages`, `json_schema` и `temperature`.
Порядок ключей словарей не влияет на ключ кэша, порядок сообщений влияет.
Ответ сохраняется в `evals/cache/<хеш>.json`: `text`, исходный `usage` и `tool_calls`.
При чтении восстанавливается `LLMResponse` с теми же текстом и вызовами инструментов,
но с нулевым расходом токенов текущего запроса.

Папка кэша создаётся при первой записи и уже исключена из Git. Другую папку можно
передать параметром `cache_dir`. Параметр `enabled=False` отключает и чтение, и запись:
каждый запрос передаётся клиенту. Для независимых повторов эксперимента кэш нужно
отключать. Флаг командной строки для этого подключается на этапе runner.

## Где хранятся результаты

Каждый запуск runner создаёт папку `evals/results/<дата и время>/`, в ней два файла:

- `runs.jsonl` — подробности каждого прогона, по одной строке на прогон: тест-кейс, вариант агента, модель, весь диалог, журнал событий, разметка судьи, оценка кода с объяснением, токены и время. Нужен, чтобы разбираться, почему агент повёл себя так или иначе.
- `summary.csv` — итоговая таблица. Каждая строка соответствует паре «модель и вариант агента», каждый столбец — одной метрике. Открывается в Excel или Google Таблицах.

Кроме того, ведём файл `evals/EXPERIMENTS.md`, журнал экспериментов. В него записываем, что поменяли, где лежат результаты и какой из этого вывод.

Задачи по порядку в [tasks.md](tasks.md#егор).
