# Проверка скила и данные (Егор)

Эта часть отвечает на вопрос, насколько скил улучшает поведение агента на разных моделях и сколько это стоит. Набор задач для проверки и формулы метрик взяты из `skill_test_cases.md`.

## Как устроена проверка

Проверка идёт автоматически, без участия человека. Для каждого тест-кейса, каждого варианта агента и каждой модели:

1. Создаётся новый агент с нужным конфигом и моделью.
2. Агенту отправляется исходная просьба из тест-кейса.
3. Агент и симулятор пользователя переписываются, пока агент не пришлёт код или не будет достигнут лимит вопросов.
4. Судья читает получившийся диалог и размечает его.
5. Код считает метрики по разметке и проверяет, правильно ли работает присланный код.
6. Всё сохраняется в файлы.

Программа, которая всё это выполняет, называется runner и лежит в `evals/run.py`. При запуске ей указывают, какие варианты агента и какие модели проверять и сколько раз повторить каждый прогон. Повторы нужны, потому что модель даже при одинаковых условиях иногда отвечает по-разному.

## Тест-кейсы

Каждый тест-кейс из `skill_test_cases.md` переносится в отдельный файл формата YAML в папке `evals/cases/clarification/`. Чтобы добавить новый тест-кейс, достаточно добавить новый файл.

Что хранится в файле тест-кейса:

| Поле | Что означает |
| --- | --- |
| `id` | номер кейса |
| `category` | группа кейса. A: в просьбе не хватает важных деталей, спрашивать нужно. B: просьба описана полностью, спрашивать не нужно. C: часть деталей указана, спрашивать нужно только о недостающих. D: простая задача, на которой проверяем, что агент не задаёт лишних вопросов |
| `prompt` | исходная просьба пользователя |
| `critical` | детали, о которых агент должен спросить, и ответ пользователя на каждую |
| `free` | детали, которые агент может решить сам |
| `expected_questions` | сколько вопросов разумно задать: минимум и максимум |
| `check` | как проверить код из ответа. Для Python это код с проверками, который можно выполнить |

Сейчас тест-кейсов 13: A1–A4, B1–B3, C1–C3, D1–D3.

## Судья

Чтобы посчитать метрики, нужно понять смысл диалога: к какой важной детали относится каждый вопрос агента и сказал ли агент о деталях, которые решил сам. Программно это не определить, поэтому это делает отдельная модель, судья. Для всех прогонов судья один и тот же, чтобы все варианты агента оценивались одинаково.

Судья получает тест-кейс и диалог и возвращает разметку в виде JSON:

- для каждого вопроса агента указано, к какой детали из `critical` он относится, или что он лишний;
- для каждой детали из `critical` указано одно из трёх: агент о ней спросил, агент решил её сам и сказал об этом, агент решил её сам и промолчал.

Судья тоже может ошибаться. Поэтому перед выводами нужно вручную проверить его разметку примерно на десяти диалогах.

## Метрики

Метрики считает обычный код по разметке судьи. Формулы взяты из `skill_test_cases.md`.

| Метрика | Что показывает | Для каких кейсов | Лучшее значение |
| --- | --- | --- | --- |
| Полнота вопросов (QR) | какую долю важных деталей агент уточнил | A, C | 1 |
| Доля озвученных допущений | какую долю важных деталей агент решил сам, но сказал об этом | A, C | |
| Доля решённого молча | какую долю важных деталей агент решил сам и не сказал | A, C | 0 |
| Точность вопросов (QP) | какая доля заданных вопросов была по делу | все | 1 |
| Лишних вопросов на прогон | сколько ненужных вопросов в среднем | все | 0 |
| Попадание в диапазон | в какой доле прогонов число вопросов попало в `expected_questions` | все | 1 |
| Ложные срабатывания | как часто агент спрашивает там, где спрашивать не нужно было вообще | B1–B3, D1, D2 | 0 |
| Тесты пройдены | работает ли присланный код: 1 полностью, 0.5 частично, 0 нет | все | 1 |

Кроме того, для каждого прогона считается стоимость: сколько потрачено токенов и секунд.

## Проверка кода

Код на Python проверяется автоматически. Из ответа агента берётся последний блок кода и запускается вместе с проверками из поля `check` тест-кейса. Запуск идёт в отдельном процессе и обрывается через 10 секунд, чтобы зависший код не остановил всю проверку. Код на JavaScript, C++ и Java пока проверяет судья по описанию из тест-кейса.

## Кэш ответов модели

Каждый прогон делает много вызовов модели, и они стоят денег. Чтобы не платить повторно за одинаковые запросы, все вызовы идут через кэш (класс `CachedLLM`).

Кэш работает так. Из названия модели, всех сообщений и параметров запроса считается хеш, то есть короткая строка, которая однозначно соответствует этому запросу. Ответ модели сохраняется в файл с этим хешем в названии. Если такой же запрос придёт ещё раз, ответ берётся из файла, и модель не вызывается.

В итоге повторный прогон без изменений ничего не стоит и даёт те же результаты. Если поменять, например, текст промпта скила, заново вызываются только те запросы, которые от этого изменились. Когда нужно специально получить новые ответы модели, кэш отключается при запуске.

## Где хранятся результаты

Каждый запуск runner создаёт папку `evals/results/<дата и время>/`, в ней два файла:

- `runs.jsonl` — подробности каждого прогона, по одной строке на прогон: тест-кейс, вариант агента, модель, весь диалог, журнал событий, разметка судьи, результат проверки кода, токены и время. Нужен, чтобы разбираться, почему агент повёл себя так или иначе.
- `summary.csv` — итоговая таблица. Каждая строка соответствует паре «модель и вариант агента», каждый столбец — одной метрике. Открывается в Excel или Google Таблицах.

Кроме того, ведём файл `evals/EXPERIMENTS.md`, журнал экспериментов. В него записываем, что поменяли, где лежат результаты и какой из этого вывод.

Задачи по порядку в [tasks.md](tasks.md#егор).
