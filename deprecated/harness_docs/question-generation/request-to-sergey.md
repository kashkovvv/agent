# Запрос к Сергею: интеграция Clarification Engine в MVP


## 1. Что предоставляю

Сохраняю предложенный интерфейс:

```python
async def assess(inp: AssessmentInput) -> Assessment: ...
async def parse_answers(inp: AnswerInput) -> AnswerParse: ...
```

assess возвращает ASK / PROCEED / ABORT, параметры, пробелы, вопросы, допущения и usage. parse_answers возвращает ANSWER / UNCLEAR / CANCEL / NEW_REQUEST, разобранные ответы, пользовательские параметры и неотвеченные вопросы.

Модуль не пишет в БД и не вызывает инструменты. Формирование событий, сохранение состояния и переходы статусов остаются у оркестратора.

## 2. Что нужно на входе

Достаточно данных из твоего текущего API:

- задача с исходным запросом и актуальным frame;
- контекст и история текущей задачи;
- заданные вопросы со статусами и ответы;
- доступные проекты с ID и именами;
- причина анализа, uncertainty и лимиты вопросов/раундов;
- при разборе ответа — исходное сообщение и открытые вопросы в порядке показа пользователю.

Новый метод поиска и обязательный список инструментов в первой версии не нужны. Для MVP фиксируем сценарии чтения и поиска по проекту; движок не пытается планировать произвольные действия.

## 3. Единственное изменение модели поведения

Предлагаю разрешить `assess.resolved_slots` с источником USER, если параметр явно взят из пользовательского сообщения текущей задачи. В evidence передаю ссылку на это сообщение. Найденное в переданном контексте остаётся CONTEXT.

Причина: в запросе «Найди команду unit-тестов backend» уже есть проект и область тестов. Не нужно задавать вопрос, чтобы записать эти сведения как пользовательские.

Нужно согласованно обновить твою проверку источников. Остальные поля AssessmentInput/Assessment и AnswerInput/AnswerParse менять не предлагаю. Правило `parse_answers.resolved_slots → USER` сохраняем.

## 4. Согласовать поведение в четырёх местах

1. **PROCEED.** Открытых блокирующих пробелов нет; можно начать допустимую работу. Неизвестная команда запуска не блокирует задачу «найти команду», если проект известен и доступны чтение/поиск. Новый критичный пробел во время выполнения идёт через существующий request_clarification.
2. **Частичный ответ.** Я возвращаю только понятые ответы, остальные — в unanswered. Сохраняем твой переход unanswered → skipped → повторный assess. Исходное сообщение остаётся в истории; новые статусы не вводим.
3. **Отмена и замена.** CANCEL и NEW_REQUEST только при явном намерении. Неоднозначное сообщение → UNCLEAR. Обычный ответ с уточнением не должен сам по себе отменять задачу.
4. **Приоритет вопросов.** Сначала блокирующие, затем остальные; внутри группы — моя эвристика полезности из описания модуля. В Question.priority передаю убывающие ранги выбранных вопросов, чтобы твоя сортировка сохранила этот порядок; исходный score вычисляется внутри движка. Поля модели не меняем.

Найденные слоты нужно применять и сохранять также при ASK, как уже описано в подробном разборе оркестрации. Так не потеряется известная часть задачи, пока пользователь отвечает на оставшийся вопрос.

## 5. LLM и ошибки

Нужен общий LLMClient через конструктор и согласованное число попыток. Временные ошибки обрабатываю ограниченными повторами, невалидную структуру пробую исправить один раз. Уточним, выполняет ли адаптер собственные повторы, чтобы они не перемножались.

При успешном результате отдаю доступный usage внутренних вызовов. Неустранимую техническую ошибку передаю исключением; твоя существующая обработка ошибок сохраняется. Никакого PROCEED по умолчанию после сбоя.

## 6. Что передать для разработки

- Общие `models`, `ports`, `errors` и функцию создания ID.
- Контрактные проверки Clarification Engine.
- Fake LLM и пример подключения движка к Orchestrator.
- Полные примеры входа/выхода для initial, after_answer и execution_uncertainty.

В предоставленной копии есть документация, но перечисленного в ней каркаса нет. Первая интеграция начинается с получения этих файлов и согласования USER из assess.

## 7. Минимальная совместная проверка

Два проекта → один вопрос → ответ backend → повторный анализ → PROCEED. Дополнительно: проект указан сразу; частичный ответ; UNCLEAR; явная отмена; исчерпание раундов. Критерий — корректное состояние задачи и отсутствие нарушений согласованного контракта.
