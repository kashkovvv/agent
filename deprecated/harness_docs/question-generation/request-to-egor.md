# Запрос к Егору: данные для Clarification Engine в MVP


Мой модуль получает всё через оркестратор Сергея. Прямых вызовов Storage или Context Engine из Clarification Engine не будет. Новые методы и таблицы для первой версии не предлагаю.

## 1. Что нужно от контекста

Подходит существующий `ContextBundle`: блоки с текстом, источником, ID, total_tokens и truncated.

Для моего модуля важно:

- понимать, из какого сообщения или файла получен факт;
- получать контекст выбранного проекта, не смешанный с другим;
- видеть исходный текст, достаточный для проверки найденного значения;
- различать пустую выдачу и обрезанный контекст по существующим полям.

Если проект пока неизвестен, используем доступный контекст чата и памяти согласно текущей схеме. После выбора проекта оркестратор повторно вызывает gather уже для него.

Пустой bundle означает только, что в выдаче нет подходящих блоков. Движок не будет делать из этого вывод, что во всём репозитории ответа нет.

## 2. Что нужно от истории

Через оркестратор получаю:

- исходный запрос и сообщения текущей задачи в хронологическом порядке;
- ранее заданные вопросы с ID, slot_name, round и status;
- ответы с question_id и raw_message_id;
- текущий frame со значениями, источниками и evidence;
- проекты с устойчивыми ID и понятными именами.

Роль и ID сообщения нужны, чтобы отличить прямое указание пользователя от текста ассистента или документа. Это особенно важно для предлагаемого извлечения USER-слотов из первого запроса.

## 3. Сохранение результата

Сохраняем предусмотренные твоим API гарантии: атомарность, порядок, отсутствие потери полей и неизменность переданных ID.

Один пользовательский текст может отвечать на несколько вопросов — несколько Answer могут ссылаться на один raw_message_id. Нормализованное значение не заменяет исходное сообщение: оно нужно при повторном анализе.

Для частичных ответов оставляем существующее поведение: понятые ответы сохраняются, остальные вопросы становятся skipped по команде оркестратора. Новых причин пропуска и статусов в MVP не добавляем. Смысл «не знаю» или «не понял вопрос» движок читает из истории.

## 4. Что нужно для начала разработки

Достаточно нескольких небольших примеров данных:

1. Два проекта и пустой контекст.
2. Выбранный проект и README с нужным фактом.
3. История: запрос → вопрос → ответ пользователя.
4. Частичный ответ на два вопроса.
5. Обрезанный ContextBundle.

Для локальной разработки подойдут объекты общих моделей или фикстуры. Реальную БД подключим на интеграции вместе с оркестратором.

## 5. Совместная проверка

Пользователь выбирает backend → ответ и USER-слот сохраняются → gather получает backend → повторный assess видит новое значение и контекст этого проекта. Дополнительно проверяем, что после записи и чтения не потерялись evidence, ID вопросов и исходные сообщения.

Отдельного поиска по запросу Clarification Engine, новых метаданных блоков и специального хранения снимков контекста для первой версии не требую. Если они понадобятся по результатам интеграции, обсудим отдельно.
