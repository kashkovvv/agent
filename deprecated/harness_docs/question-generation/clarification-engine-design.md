# Clarification Engine: устройство MVP


Основа — два метода и модели из `clarification-engine-api.pdf`, подготовленного Сергеем. Сохраняем его схему оркестрации; ниже уточняем поведение нашего модуля.

## 1. Задача и границы

Clarification Engine определяет, хватает ли данных для работы, задаёт необходимые уточняющие вопросы и разбирает ответы пользователя.

В MVP модуль:

- использует исходный запрос, известные параметры и переданный контекст;
- возвращает решение `ASK`, `PROCEED` или `ABORT`;
- формулирует до трёх вопросов за раунд;
- извлекает из ответа значения параметров;
- отличает ответ от явной отмены или явной замены задачи.

Модуль не пишет в БД, не вызывает инструменты и не общается с пользователем напрямую. Всё это делает оркестратор Сергея. Контекст и сохранённую историю предоставляет Егор через оркестратор. Для понимания текста движок использует переданный `LLMClient`.

## 2. Интерфейс

```python
async def assess(inp: AssessmentInput) -> Assessment: ...
async def parse_answers(inp: AnswerInput) -> AnswerParse: ...
```

### assess: достаточно ли информации

Оркестратор вызывает метод при новой задаче, после ответа пользователя и при неопределённости во время выполнения.

На входе уже предусмотрены:

- `task` — запрос и известные параметры в `frame`;
- `context` — отобранные блоки контекста;
- `history`, `asked`, `answers` — история задачи, вопросы и ответы;
- `projects` — список проектов для выбора;
- `trigger`, `uncertainty` — причина анализа;
- `round`, `max_questions`, `rounds_left` — номер раунда и ограничения.

На выходе — существующая модель `Assessment`: решение, цель, найденные параметры, пробелы, вопросы, допущения, объяснение и `usage`.

- **ASK:** осталось что-то критичное и можно спросить. Возвращаем от одного до `max_questions` вопросов.
- **PROCEED:** открытых блокирующих пробелов нет. Для некритичных параметров допустимы явно обозначенные допущения.
- **ABORT:** продолжить нельзя, например критичный параметр не определён, а раунды закончились. Возвращаем понятную причину.

### parse_answers: что сообщил пользователь

На входе — `task`, открытые вопросы `pending`, новое `message` и `projects`.

На выходе — существующая модель `AnswerParse`:

- `ANSWER` — удалось извлечь хотя бы один ответ;
- `UNCLEAR` — однозначного ответа нет;
- `CANCEL` — пользователь явно отменил задачу;
- `NEW_REQUEST` — пользователь явно попросил заменить задачу другой.

Возвращаем ответы с `question_id`, найденные пользовательские параметры, список неотвеченных вопросов и `usage`. Ответы привязываем только к вопросам из `pending`. У CANCEL и NEW_REQUEST ответов нет.

## 3. Как работает assess

1. Прочитать запрос, `frame`, историю и контекст; выделить уже известные параметры.
2. Определить, каких сведений не хватает именно для этой задачи.
3. Разделить пробелы на блокирующие и неблокирующие.
4. Проверить, нет ли ответа в уже переданных данных.
5. Выбрать ASK / PROCEED / ABORT с учётом оставшихся раундов.
6. Если нужен ASK — выбрать самые полезные вопросы, убрать дубли, сформулировать их понятно.
7. Проверить результат обычным кодом и вернуть его оркестратору.

LLM помогает понимать свободный текст и формулировать вопросы. Ограничения на число вопросов, допустимость ID, источники и структуру ответа проверяет код. Это дополняет проверку оркестратора, а не заменяет её.

### Что считать блокирующим

Блокирующий пробел мешает начать допустимую работу без существенной догадки. Например, запрос относится к одному проекту, а в чате их два и выбор не указан.

Не всякая неизвестная деталь — блокер. Для задачи «Найди команду запуска тестов backend» сама команда является результатом поиска. Её отсутствие на входе не мешает начать читать файлы известного проекта. Для общего вопроса «Что такое unit-тест?» проект вообще не требуется.

В MVP не добавляем отдельный цикл поиска внутри Clarification Engine. Движок анализирует только полученные данные; обычный поиск после PROCEED выполняет агент через оркестратор. Если там возникает критичная неопределённость, используется уже предусмотренный `request_clarification`.

## 4. Правила вопросов и ответов

### Вопросы

- Не спрашивать то, что пользователь уже сообщил или что однозначно известно из контекста.
- Не более одного вопроса на слот и не более трёх за раунд; один вопрос лучше трёх, если его достаточно.
- Сначала выбирать блокирующие вопросы; внутри группы использовать эвристику полезности вопросов, предложенную Родионом.
- Не выдумывать варианты проектов; `project_id` должен соответствовать переданному `Project.id`.
- Допущение не закрывает блокирующий пробел.
- При `rounds_left=0` возвращать ABORT при открытом блокере, иначе PROCEED.

Сортировку и итоговый `priority` согласуем с Сергеем: после его проверки выбранные блокирующие вопросы не должны вытесняться менее важными.

### Эвристика выбора вопросов

Для ранжирования используем предложенную Родионом эвристику, отражённую в текущем описании API:

```text
score = 3 × blocking + 2 × information_gain + impact − user_cost − available_in_context
```

- `blocking` — 1, если пробел блокирует работу, иначе 0.
- `information_gain` — насколько ответ уменьшит неопределённость.
- `impact` — насколько параметр влияет на результат задачи.
- `user_cost` — насколько сложно пользователю ответить.
- `available_in_context` — оценка доступности ответа в переданных данных.

Последние четыре оценки лежат в диапазоне от 0 до 1. Их предлагает LLM при анализе пробелов, а код проверяет диапазоны и вычисляет score. Это простая эвристика для MVP, а не измеренная вероятность; начальные веса фиксируем и проверяем на основных сценариях.

Если ответ уже однозначно найден в контексте, вопрос исключаем ещё до ранжирования. Среди оставшихся сначала рассматриваем блокирующие вопросы, затем неблокирующие; внутри каждой группы сортируем по score. Отбираем не более K вопросов, без повторов по слоту. Заполнять все K мест необязательно.

Сам коэффициент 3 не гарантирует, что любой блокирующий вопрос получит оценку выше любого неблокирующего, поэтому группировка выполняется отдельно. Чтобы оркестратор сохранил выбранный порядок при сортировке по `Question.priority`, передаём в этом поле убывающие ранги от числа выбранных вопросов до 1. Score остаётся внутренней оценкой; новых полей API не требуется.

Например, неизвестный проект с оценками `1, 1, 1, 0.1, 0` получает score=5.9. Предпочтение формата с оценками `0, 0.2, 0.3, 0.4, 0` получает score=0.3. Вопрос о проекте идёт первым; формат можно принять по умолчанию, если он не влияет существенно на задачу.

### Ответы

- «backend» при однозначном выборе проекта → ответ с соответствующим ID.
- «1 — backend, 2 — кратко» → ответы по номерам показанных вопросов.
- «backend, остальное не знаю» → сохранить только понятую часть; остальные вопросы вернуть в `unanswered`.
- Неоднозначное «да» к нескольким вопросам → UNCLEAR, без догадок.
- «Не отменяй, backend» → ответ, а не CANCEL.
- «Вместо этого объясни README» → NEW_REQUEST.

Для MVP сохраняем существующее поведение оркестратора: вопросы без ответа становятся `skipped`, затем снова вызывается assess. Новых статусов и причин пропуска не добавляем. По исходному сообщению в истории движок может понять «не знаю» или непонимание и не повторять вопрос механически.

Смешанные сообщения с несколькими новыми задачами не пытаемся автоматически раскладывать в очередь. Если смысл неоднозначен, возвращаем UNCLEAR, не отменяя задачу по догадке.

## 5. Одно изменение контракта на согласование

В текущем API `assess.resolved_slots` допускает только `CONTEXT`. Но параметры могут быть явно указаны уже в первом запросе: «Найди команду unit-тестов backend».

**Предлагаю разрешить из assess также `source=USER` для явных значений из пользовательских сообщений текущей задачи.** У каждого такого значения должна быть ссылка на сообщение в `evidence`. Значения из блоков контекста остаются CONTEXT. Проверку источника у Сергея нужно изменить соответственно.

Это позволяет не переспрашивать уже сказанное и сохранить приоритет пользовательского указания. Остальные формы входа/выхода сохраняем. Расширение assess на TOOL, новые типы вариантов и новые поля состояния в этот MVP не включаем.

## 6. LLM и ошибки

Движок получает общий LLMClient через конструктор. Для сложного текста просит структурированный результат, затем проверяет его. Очевидные случаи можно обрабатывать правилами.

При временном сбое допустимы ограниченные повторы; число попыток согласуем с Сергеем, чтобы не дублировать ретраи адаптера. При невалидном ответе допускаем одну попытку исправления структуры. Если получить корректный результат не удалось — исключение, которое оркестратор обрабатывает по существующему контракту. Ошибка модели не должна превращаться в PROCEED.

В `usage` успешного результата суммируем доступные сведения о затратах всех внутренних попыток. Ориентир assess — около 10 секунд, как в запросе Сергея; фактическую задержку измеряем на первой версии.

## 7. Пример работы

Пользователь: «Найди команду запуска тестов проекта». В чате backend и frontend.

1. Оркестратор создаёт задачу и получает контекст.
2. assess видит, что проект не определён, и возвращает ASK: «Для какого проекта: backend или frontend?».
3. Оркестратор сохраняет вопрос и ждёт пользователя.
4. Пользователь отвечает «backend». parse_answers возвращает `project_id=p_backend` с источником USER.
5. Оркестратор сохраняет ответ и заново собирает контекст выбранного проекта.
6. assess возвращает PROCEED: проект определён, можно искать команду.
7. Исполнитель читает файлы и сообщает результат поиска. Запуск тестов в этом примере не предполагается.

## 8. План и готовность первой версии

1. Согласовать интерфейсы, получить общие модели и контрактные тесты Сергея.
2. Реализовать базовый сценарий на правилах: выбор проекта, разбор ответа, лимит раундов.
3. Добавить LLM для свободных формулировок и проверку структурированного результата.
4. Подключить модуль к оркестратору и прогнать основные сценарии.

Первая версия готова, когда она:

- спрашивает о действительно неизвестном проекте и не спрашивает об уже указанном;
- правильно разбирает однозначные, частичные и непонятные ответы;
- не разрешает выполнение с открытым блокером и не превышает лимиты;
- корректно распознаёт явную отмену и замену задачи;
- возвращает результаты, которые проходят общие контрактные проверки.

Дополнительно измеряем число лишних вопросов, число неверных решений PROCEED, точность извлечения ответов и задержку. Оценка на сценариях не означает гарантию правильности на любых запросах.

## 9. Что остаётся за пределами MVP

Отдельный поиск по инициативе движка, очереди новых задач, расширенные статусы вопросов, универсальная обработка исправлений со сбросом зависимых параметров, новые механизмы восстановления и сложный учёт бюджета. Они не являются условиями готовности первой версии Clarification Engine.
