# AI Agent Harness: уточняющие вопросы

**Кратко для ментора · Родион**

Статус: проект модуля для MVP. Документ описывает предлагаемое поведение; реализация и результаты тестов пока не заявлены.

## Задача

Мы делаем harness вокруг готовой LLM, который помогает не додумывать критичные параметры задачи.

Моя часть — Clarification Engine. Если в запросе не хватает важных сведений, модуль определяет, что именно нужно узнать, и формулирует уточняющие вопросы. После ответа пользователя он извлекает значения параметров, чтобы агент мог продолжить работу.

Например, при двух проектах в чате нельзя самостоятельно выбрать один по запросу «Найди команду запуска тестов проекта». Сначала нужно уточнить проект. Если пользователь уже указал backend, повторный вопрос не нужен.

В MVP не обучаем модель: используем готовую LLM через общий клиент и проверяем её структурированные ответы обычным кодом.

## Место в архитектуре

Оркестратор Сергея вызывает Clarification Engine, передаёт задачу, контекст и историю, а затем сохраняет и исполняет решение. Егор отвечает за хранение и сбор контекста.

Clarification Engine не пишет в БД, не показывает вопросы пользователю и не вызывает инструменты. Его интерфейс состоит из двух методов:

- `assess` — хватает ли данных: ASK / PROCEED / ABORT;
- `parse_answers` — что ответил пользователь и какие параметры стали известны.

## Как обрабатывается запрос

Пример: «Найди команду запуска тестов проекта», в чате backend и frontend.

1. Оркестратор создаёт задачу и собирает контекст.
2. assess обнаруживает, что проект неизвестен, и возвращает вопрос «Для какого проекта: backend или frontend?».
3. Оркестратор сохраняет вопрос и переводит задачу в ожидание ответа.
4. Пользователь пишет «backend». parse_answers связывает ответ с вопросом и возвращает ID выбранного проекта.
5. Оркестратор сохраняет параметр и повторно собирает контекст.
6. assess разрешает продолжение. Исполнитель ищет команду в файлах проекта и сообщает результат.

Этот пример использует возможности текущего MVP: чтение и поиск файлов, без запуска тестов.

## Моя часть: ключевые решения

- **Сначала использовать известное.** Проверять запрос, параметры и переданный контекст до генерации вопросов.
- **Различать критичное и некритичное.** Неизвестный проект может блокировать работу; предпочтение формата ответа обычно допускает разумное значение по умолчанию.
- **Ограничить уточнения.** До трёх вопросов за раунд и до трёх раундов по текущим настройкам оркестратора. Если критичное не выяснено, возвращать отказ с причиной.
- **Сохранять простую обработку ответов.** Извлекать понятую часть; непонятную не угадывать. Использовать существующие статусы и повторный анализ.
- **Проверять результат LLM.** Контролировать число вопросов, ссылки на вопросы, допустимость ID проекта и структуру ответа. Допущения не закрывают блокирующие пробелы.

## Что прошу у коллег

**У Сергея:** общие модели, LLMClient, контрактные тесты и входные данные из уже описанного API. Предлагаю одно изменение правила: разрешить assess возвращать USER-слоты из явных пользовательских сообщений со ссылкой на источник. Это нужно, чтобы правильно учитывать параметры уже в первом запросе.

**У Егора:** контекст с источниками, хронологическую историю, сохранённые вопросы и ответы, список проектов. Всё передаётся через оркестратор; новых методов хранения для моего MVP не требуется.

## Статус и план

Подготовлены описание модуля, встречные требования к коллегам и основные сценарии приёмки. Следующие шаги:

1. Согласовать интерфейс и получить каркас с общими моделями.
2. Реализовать базовый цикл уточнения на правилах.
3. Подключить LLM для свободных запросов и ответов.
4. Проверить модуль отдельно и вместе с оркестратором.

Оценивать будем правильность решения ASK/PROCEED, число лишних вопросов, точность разбора ответов и задержку. Прохождение контрактных тестов проверяет формат и ограничения; смысловое качество проверяем на примерах.
