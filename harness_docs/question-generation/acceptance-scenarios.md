# Основные сценарии приёмки MVP

Статус: проект проверок, не отчёт о выполненных тестах.

Проверяем два метода и базовый цикл оркестрации. Не требуем универсальной обработки всех вариантов диалога. Сложные или неоднозначные ответы не угадываем: используем существующий UNCLEAR и повторный assess в пределах лимита.

Точный текст вопроса может меняться. Проверяем его смысл, нужный параметр и корректность результата по общим моделям.

## 1. Неизвестен проект

**Вход:** «Найди команду запуска тестов проекта», в чате backend и frontend, выбор нигде не указан.

**Ожидаем:** ASK, вопрос о проекте с доступными вариантами. Не выбираем проект за пользователя.

## 2. Проект указан в запросе

**Вход:** «Найди команду unit-тестов backend»; backend однозначно соответствует одному проекту.

**Ожидаем:** не спрашивать заново проект и область тестов; вернуть найденные значения со ссылкой на сообщение. USER из assess проверяется после согласования этого изменения с Сергеем.

## 3. Сведения есть в контексте

**Вход:** проект известен, README в переданном контексте содержит нужную команду.

**Ожидаем:** PROCEED без вопроса о команде. Если возвращаем найденный параметр, его источник — CONTEXT.

Если команда ещё не найдена, но задача состоит именно в её поиске по известному проекту, это также не повод спрашивать команду у пользователя: поиск выполняется обычным циклом агента.

## 4. Проект не нужен

**Вход:** «Объясни, что такое unit-тест».

**Ожидаем:** PROCEED без уточнения проекта.

## 5. Понятный ответ на вопрос

**Вход:** открытый вопрос о проекте, ответ «backend».

**Ожидаем:** ANSWER, корректные question_id и Project.id, параметр с источником USER. После сохранения и повторного анализа этот вопрос больше не задаётся.

Для двух независимых вопросов дополнительно проверяем ответ «1 — backend, 2 — кратко»: значения должны попасть к соответствующим вопросам в порядке показа.

## 6. Частичный или непонятный ответ

**Вход:** два вопроса; пользователь ответил только на один.

**Ожидаем:** сохранить понятую часть, остальные ID вернуть в unanswered. Оркестратор использует существующий skipped и повторный assess. Новых статусов не нужно.

Если ни одного однозначного ответа нет, например пришло непонятное «да», ожидаем UNCLEAR без выдуманных значений.

## 7. Явная отмена или замена

**Вход:** «Отмени задачу» → CANCEL. «Вместо этого объясни README» → NEW_REQUEST.

**Ожидаем:** в обоих результатах нет answers; дальнейшее действие выполняет оркестратор по текущему контракту. Неоднозначное сообщение не должно отменять задачу по догадке.

## 8. Лимит вопросов и раундов

**Вход:** max_questions=3; отдельно — rounds_left=0.

**Ожидаем:** при ASK от одного до трёх вопросов, не больше одного на слот. При нуле раундов — ABORT, если остался блокер, иначе PROCEED. Допущение не закрывает блокер.

## 9. Неопределённость при выполнении

**Вход:** assess с trigger=execution_uncertainty и описанием недостающего критичного параметра, которого нет в истории и контексте.

**Ожидаем:** обработать его теми же правилами: ASK при наличии раундов, иначе ABORT. Отдельный механизм поиска или восстановления внутри движка не требуется.

## 10. Ошибка LLM

**Вход:** после предусмотренных ограниченных попыток не удалось получить корректный структурированный результат.

**Ожидаем:** исключение для существующего обработчика оркестратора. Не возвращаем PROCEED как запасной вариант и не повторяем вызовы бесконечно.

## Когда считать первую версию готовой

Основные сценарии и общие контрактные проверки проходят. Совместный пример «запрос → вопрос → ответ → PROCEED» работает с сохранением данных. Для живой LLM отдельно фиксируем замеченные смысловые ошибки и время ответа; сами документы не утверждают, что проверки уже выполнены.

Исправления прежних параметров со сбросом зависимостей, смешанные новые задачи, сложные конфликты источников и восстановление после сбоев не добавляем в критерии приёмки этого модуля. Они не требуют новых веток MVP; неоднозначный ответ обрабатывается существующим UNCLEAR.
