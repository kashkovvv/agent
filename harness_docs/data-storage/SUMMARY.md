# Storage и Context Engine: краткий итог MVP

Основной документ — [storage-design.md](storage-design.md). Проект подготовлен по API Сергея; открытые вопросы требуют согласования. Код пока не пишем, SQL не применяем.

## Что проектируем

- **Storage** читает и сохраняет данные. Семь репозиториев: `tasks`, `messages`, `clarifications`, `tool_runs`, `snapshots`, `projects`, `inbox`.
- **Context Engine** методом `gather(query)` выбирает доступные сведения и возвращает `ContextBundle`: фрагменты с источниками, оценкой полезности и числом токенов.
- **Сергей** управляет шагами и состоянием задачи, собирает промпт. **Родион** определяет пробелы и вопросы; данные получает через оркестратор.

## Основа первой версии

Одна PostgreSQL, один пользователь, один процесс оркестратора. В [schema.sql](schema.sql) — **11 таблиц**: чаты, проекты, связи чатов с проектами, задачи, сообщения, вопросы, ответы, запуски инструментов, снимки, `inbox` и блоки контекста.

Текущая задача хранится в `tasks`, её карточка — целиком в JSONB `frame`. Снимки нужны для истории. `inbox` связывает ключ принятого сообщения с задачей и защищает от повторов.

Обязательные гарантии: общая транзакция через Unit of Work; обновление задачи по версии (CAS); одна активная задача на чат; модели без потерь; порядок записей; неизменность ID; время UTC.

Контекст подбираем простым поиском по словам и давности из разрешённых источников. Историю текущей задачи повторно не добавляем. Соблюдаем бюджет, сохраняем происхождение. Готовый промпт собирает Сергей.

## Что откладываем и что уточняем

За пределами MVP — полные логи LLM, отдельное наполнение памяти, векторный поиск, автоматические summaries и хранение текстов по аналогии с Git blob. SQL-дополнения для памяти и трассировки остаются материалом на будущее.

Нужно согласовать SHA-256 в API, регистрацию проектов и путей, доступ к другим чатам, подсчёт токенов, глобальность ключей `inbox` и точные модели. Для реализации нужны отсутствующие здесь исходники контрактов и проверок Сергея.
